# s5-pmrt-arm, packaged as an akmod

The mitigation's kernel module is not compiled by hand: `akmods` rebuilds it
automatically for every new kernel and installs it at
`/lib/modules/<version>/extra/s5-pmrt-arm/s5_pmrt_arm.ko.xz`.

**The source is `s5-pmrt-arm-1.0/kernel/s5_pmrt_arm.c`, a plain file in this
directory.** The tarball and the RPMs are build products: they are generated by the
commands below and deliberately not versioned, so that the module — the technical
heart of the project — stays readable, searchable and diffable on its own.

## Building and installing the module

From this directory (`kmod/` in the repo):

    tar czf s5-pmrt-arm-1.0.tar.gz s5-pmrt-arm-1.0      # the spec's Source0
    mkdir -p rpmbuild/SOURCES rpmbuild/SPECS
    cp s5-pmrt-arm-1.0.tar.gz  rpmbuild/SOURCES/
    cp s5-pmrt-arm-kmod.spec   rpmbuild/SPECS/          # akmod re-invokes rpmbuild and looks for it HERE
    rpmbuild --define "_topdir $PWD/rpmbuild" -bb s5-pmrt-arm-kmod.spec
    sudo dnf -y install --nogpgcheck --disablerepo='*' rpmbuild/RPMS/*/*.rpm
    sudo akmods --force --kernels "$(uname -r)"
    s5-mitigacion-check

## Changing the module

    $EDITOR s5-pmrt-arm-1.0/kernel/s5_pmrt_arm.c
    # bump Release: in s5-pmrt-arm-kmod.spec and add a %changelog entry

then run the build block above again.

**`devs=` has no default and that is deliberate.** The module shields exactly the BDFs
it is given; the shutdown hook always passes the list that `s5-descubre-dgpu` found. A
hand-run `modprobe s5_pmrt_arm arm=1` with no `devs=` is refused with `-EINVAL` rather
than silently shielding whatever happens to sit at some other machine's addresses.

You need `rpmbuild`, `kmodtool` and `kernel-devel`. On Fedora:
`sudo dnf install rpm-build akmods kernel-devel`.

**Outside Fedora/RHEL/SUSE there is no `akmods`.** The equivalent is DKMS: the tarball's
`Makefile` works as-is, but you will need to write a `dkms.conf`. What you must **not**
do is compile the `.ko` by hand and forget about it — see below.

## Checking it is still alive

    s5-mitigacion-check          # report; rc=1 if anything is wrong
    systemctl status s5-mitigacion-check.service

It runs itself on every boot, ordered after `akmods.service`.

## Why an akmod and not a hand-built .ko

A `.ko` carries the `vermagic` of the kernel it was built against. After the first kernel
update `insmod` rejects it and **the mitigation dies silently**: the shutdown looks just
as good and costs 18-20 W again. That is why it is packaged, and why
`s5-mitigacion-check` verifies on every boot that a loadable module exists for the
**running** kernel.

## Details that cost an afternoon to discover

The akmod installs the module **compressed** (`.ko.xz`), and `insmod` cannot load that:
the `99y` hook uses `modprobe`. It also keeps an `insmod` fallback against a loose `.ko`
(see `KO=` in the hook — empty unless you set `S5_KO_RESPALDO=` in
`/etc/s5-poweroff-fix.conf`), which leaves a `via=RESPALDO-insmod(akmod fallo)` witness in
the log when it is used.

And **`modprobe` returns 0 if the module was already loaded, without re-running its
init** — so nothing gets shielded, with the log showing success. All of this module's work
happens in its init: loading it *is* the action. The hook does an `rmmod` first for that
reason; if you chain rehearsals by hand, do the same.
